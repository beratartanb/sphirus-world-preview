# SHME V1.1: physical execution pass (2026-09-25)

**Acceptance: PARTIAL V1.1.**

**Delivered:**
- The foot plan is now an actionable, reach-bounded and ground-validated plan.
- An execution state machine (with hysteresis) drives two real integrations:
  - landing support, through the existing FootPlacement;
  - a bounded post-stop settle.
- These materially fix the walking-jump landing (51 → 8 cm) and the sprint-stop idle settle (19 → 10 cm), with every protected row intact.

**Not delivered:**
- The diagonal-stop slide: its root cause is in the animation data.
- A visible 45/90/180 body difference from PBI.
- A measured benefit from Motion Matching guidance.
- Real-time, physical-device and real-house review.

## 1. Architecture changes (inside the V1 SHME component; nothing rebuilt)

| Change | What it does |
|---|---|
| `SHM_UpdateFootPlan` (rewritten) | Capture point → anatomical reach region (facing frame around the support foot: forward 70 / back 40 / lateral 35 cm) → ground line trace (slope ≤ ~35°, step ≤ 40 cm). Outputs FootTarget, FootTargetFacing, SwingSide, StepUrgency, FootTargetConfidence, RecommitDemand (target exceeded reach), FootPlantStrength |
| `SHM_UpdateExecution` (new) | 9-state machine with a dwell hysteresis of 0.08 s: none, minor weight shift, support transfer, committed plant, recovery step, brake-and-replant, reversal recommit, landing support, post-stop stabilise |
| `SHM_UpdateSettle` (new) | One bounded capsule settle per real stop, toward the projected COM |
| `SHM_PerfLap*` (new) | Per-subsystem cost timers |
| Debug view (extended) | Support/other foot confidence spheres, support→target line, execution-state text |
| Telemetry (extended) | exec, urgency, recommit, target confidence, ground validity, landing support, post-stop, stance offset, settle, cost split |

**AnimBP** (Sandbox `ABP_GR_MotionMatchingBase`, via the existing game-thread snapshot `SHM_Snapshot`):
- `SHM_LandingSupport` → `Get_FootPlacementPlantSettings` selects `PlantSettings_Landing` (the Default settings with UnplantRadius = 150) during the landing recovery window. This uses the **existing** FootPlacement node; there is no second lock system.
- `SHM_HoldStops` → the `Update_MotionMatching` entry keeps the current database (DoNotInterrupt) while post-stop stabilising. It is flag-gated and OFF by default: no measured benefit.

## 2. Support execution

- Support side, double support and reach decide the execution state and the swing foot.
- The **brake-and-replant** state gates the settle, via double support and the stance offset.
- The **landing-support** state drives the plant radius.
- At 10 FPS the states still change cleanly (reversal, brake, post-stop, transfer) without chatter.
- Support does **not** yet change pose selection or IK targets directly.

## 3. FootPlan → actual foot

- The planned target is bounded and validated, but it is **not** written into IK in V1.1.
- **Why:** the root-cause study showed the measured slides were not caused by IK aiming at the wrong spot. They came from:
  - FootPlacement releasing (landing);
  - clip data (diagonal stops);
  - capsule/COM mismatch (settle).
- The plan's execution is therefore through the plant settings (landing) and the settle.
- A "planned vs actual touchdown" target error metric is **NOT_TESTED**.

## 4. Motion Matching integration

- The minimal hook (hold the current database while stabilising after a stop) is implemented and working.
- It produced no slide improvement, because the settle glide came from idle re-centring and not from an early database switch. It is left OFF: `MotionMatchingPhysicalGuidanceEnabled = false`.
- No PoseSearch schema was changed.

## 5. Capture-point usage

The capture point now changes behaviour through:
- **StepUrgency** (capture error × confidence) → FootTargetWeight/Confidence.
- **RecommitDemand** when the capture point falls outside the reach region → FootPlantStrength drops (V1 PlantStrength is still telemetry only).
- **RecoveryDemand** → the RECOVERY_STEP execution state.

It does **not** yet select animation.

## 6. PBI coupling

A/B of blend 0 / 0.5 / 0.8 (`body_metrics.py`):
- Direction severity changes as designed.
- Visible torso lean changes by less than 0.7 cm and shoulder counter-yaw by less than 5°, with no added wobble.

Kept at 0.5. The visible 45/90/180 differences (fast 90° shoulder counter-yaw about 57° vs fast 180° about 118°) come from the animation. PBI's direction channel is too weak to add a visible consequence without raising its own gains, which is a separate tuning decision.

## 7. Before → after

30 FPS, injected input, QA fixtures. Foot-slide proxy in cm.

| Scenario | SHME off | V1 | **V1.1** | Cause / fix |
|---|---|---|---|---|
| Walking forward jump, air+landing | 51.3 | 51.3 | **8.3** | FootPlacement radius release → LandingSupport plant radius |
| Sprint stop → idle settle | 19.3 | 19.3 | **10.0** | Idle re-centres the body onto a capsule 10–14 cm behind the COM → one bounded settle |
| Walk stop (suite 2 / suite 5) | 11.1 / 9.5 | 11.0 / 9.5 | **5.9 / 6.8** | Settle |
| Sustained forward-right stop | 10.1 | 10.2 | 5.6 | Settle |
| Sustained ±45° diagonal stops | 21.6–29.1 | 21.6–29.1 | 20.7–29.1 | **Root cause:** AAMS walk-stop FL/FR clip tails drift ~29 cm with footspeed 0 while the capsule is stopped (FootPlacement on/off identical). Needs clip-range or selection work |
| Tap stops (P1) | – | – | same to within ~1 cm | Settle gated off after taps |
| Reversals F↔B, sprint 90/180 | – | – | identical | – |
| Jog stop | 2.3 | 2.3 | 3.4 | Settle side effect |
| Wall: sprint stop into wall | 0.9 | 0.9 | 4.6 | Settle side effect; the wall guard reduced it from 11.7 |
| Stairs top settle | 1.7 | 1.7 | 3.9 | Settle side effect |
| 10 FPS stops/reversals | – | – | same clips; slide within noise | – |

Other V1.1 findings:
- The idle-settle slide is **worse** with FootPlacement on than off (19.3 vs 13.4). FootPlacement holds the foot, then releases and catches up. Raising its speed or radius thresholds makes it worse (34–39 cm).
